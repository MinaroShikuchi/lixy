    Contributing to Lixy¶

    Thank you for your interest in contributing to Lixy! This document provides guidelines and instructions for contributing to the project.

    Code of Conduct¶

    Our Pledge¶

    We are committed to providing a welcoming and inspiring community for all. Please be respectful and constructive in your interactions.

    Our Standards¶

    Positive behavior includes: - Using welcoming and inclusive language - Being respectful of differing viewpoints - Gracefully accepting constructive criticism - Focusing on what is best for the community - Showing empathy towards other community members

    Unacceptable behavior includes: - Harassment, trolling, or derogatory comments - Publishing others' private information - Other conduct which could reasonably be considered inappropriate

    How to Contribute¶

    Reporting Bugs¶

    Before creating a bug report, please check existing issues to avoid duplicates.

    When filing a bug report, include: - Clear, descriptive title - Steps to reproduce the issue - Expected vs. actual behavior - Environment details (OS, Go version, etc.) - Relevant logs or error messages - Screenshots if applicable

    Bug Report Template: 

    **Description:**
A clear description of the bug.

**Steps to Reproduce:**
1. Step one
2. Step two
3. Step three

**Expected Behavior:**
What you expected to happen.

**Actual Behavior:**
What actually happened.

**Environment:**
- OS: [e.g., Ubuntu 22.04]
- Go Version: [e.g., 1.21.0]
- Lixy Version: [e.g., 1.0.0]

**Logs:**
    Paste relevant logs here 
    **Screenshots:**
If applicable, add screenshots.

    Suggesting Enhancements¶

    Enhancement suggestions are welcome! Please provide: - Clear use case description - Expected behavior - Why this enhancement would be useful - Possible implementation approach (optional)

    Pull Requests¶

    1. Fork the repository 

      git clone https://github.com/MinaroShikuchi/lixy.git
cd lixy

    2. Create a feature branch 

      git checkout -b feature/your-feature-name

    3. Make your changes

    4. Follow the coding standards (see below)
    5. Add tests for new functionality

    6. Update documentation as needed

    7. Commit your changes 

      git add .
git commit -m "feat: add new feature"

    8. Push to your fork 

      git push origin feature/your-feature-name

    9. Create a Pull Request

    10. Use a clear, descriptive title
    11. Reference any related issues
    12. Describe your changes in detail
    13. Include screenshots for UI changes

    Development Setup¶

    Prerequisites¶

    • Go 1.21 or higher
    • Git
    • LXC/LXD (for testing)
    • Make (optional, for using Makefile)

    Setting Up Development Environment¶

    # Clone the repository
git clone https://github.com/MinaroShikuchi/lixy.git
cd lixy

# Install dependencies
go mod download

# Build the controller
cd cmd/lixy
go build -o lixy

# Build the agent
cd ../lixies
go build -o lixies

# Run tests
cd ../..
go test ./...

    Coding Standards¶

    Go Code Style¶

    Follow the official Go Code Review Comments.

    Key points: - Use gofmt to format code - Use golint for linting - Follow standard Go naming conventions - Write clear, self-documenting code - Add comments for exported functions

    Example: 

    // DeploymentService manages deployment lifecycle
type DeploymentService struct {
    logger *slog.Logger
    store  *store.DeploymentStore
}

// CreateDeployment creates a new deployment
func (s *DeploymentService) CreateDeployment(name, target string, yaml []byte) error {
    // Validate inputs
    if name == "" {
        return fmt.Errorf("deployment name is required")
    }

    // Create deployment
    deployment := &store.Deployment{
        Name:        name,
        TargetLXC:   target,
        ComposeYAML: yaml,
    }

    return s.store.Create(deployment)
}

    Commit Messages¶

    Follow Conventional Commits:

    Format: 

    <type>(<scope>): <subject>

<body>

<footer>

    Types: - feat: New feature - fix: Bug fix - docs: Documentation changes - style: Code style changes (formatting, etc.) - refactor: Code refactoring - test: Adding or updating tests - chore: Maintenance tasks

    Examples: 

    feat(gitops): add drift detection support

Implement automatic drift detection for deployments.
Compares deployment hashes to detect configuration changes.

Closes #123


    fix(auth): resolve JWT token expiration issue

Fixed bug where tokens were expiring prematurely due to
incorrect time calculation.

Fixes #456

    Testing¶

    Unit Tests¶

    Write unit tests for all new functionality:

    func TestCreateDeployment(t *testing.T) {
    // Setup
    logger := slog.New(slog.NewTextHandler(os.Stdout, nil))
    store := store.NewDeploymentStore(db)
    service := NewDeploymentService(logger, store)

    // Test
    err := service.CreateDeployment("test-app", "agent1", []byte("yaml"))

    // Assert
    if err != nil {
        t.Errorf("Expected no error, got %v", err)
    }
}

    Integration Tests¶

    For features that interact with external systems:

    func TestGitOpsReconciliation(t *testing.T) {
    if testing.Short() {
        t.Skip("Skipping integration test")
    }

    // Setup test environment
    // Run reconciliation
    // Verify results
}

    Running Tests¶

    # Run all tests
go test ./...

# Run with coverage
go test -cover ./...

# Run specific package
go test ./internal/services/...

# Skip integration tests
go test -short ./...

    User Documentation¶

    Update relevant documentation when adding features: - API documentation for new endpoints - CLI documentation for new commands - User guides for new workflows - Architecture docs for significant changes

    Pull Request Process¶

    Before Submitting¶

    • Code follows project style guidelines
    • All tests pass
    • New tests added for new functionality
    • Documentation updated
    • Commit messages follow conventions
    • No merge conflicts with main branch

    Review Process¶

    1. Automated Checks: CI/CD runs tests and linters
    2. Code Review: Maintainers review your code
    3. Feedback: Address any requested changes
    4. Approval: Once approved, PR will be merged

    After Merge¶

    • Your contribution will be included in the next release
    • You'll be added to the contributors list
    • Thank you for contributing! 🎉

# ... edit files ...

# 3. Add test for the bug
# ... create test ...

# 4. Verify fix

# 5. Commit

# 6. Push and create PR
git push origin fix/issue-123

    Release Process¶

    Releases are managed by maintainers:

    1. Version bump in version.go
    2. Update CHANGELOG.md
    3. Create Git tag
    4. Build binaries
    5. Create GitHub release
    6. Update documentation

    License¶

    By contributing, you agree that your contributions will be licensed under the MIT License.

    Additional Guidelines¶

    Security Issues¶

    Do not open public issues for security vulnerabilities.

    Instead: 1. Email security@example.com 2. Include detailed description 3. Wait for response before disclosure

    Performance¶

    • Profile code for performance-critical paths
    • Avoid premature optimization
    • Document performance considerations
    • Include benchmarks for optimizations

    Dependencies¶

    • Minimize external dependencies
    • Prefer standard library when possible
    • Document why dependencies are needed
    • Keep dependencies up to date

    Breaking Changes¶

    • Avoid breaking changes when possible
    • Document breaking changes clearly
    • Provide migration guides
    • Deprecate before removing

    Thank You!¶

    Your contributions make Lixy better for everyone. We appreciate your time and effort! 🙏

    Architecture Overview¶

    This document provides a comprehensive overview of Lixy's architecture, components, and design decisions.

    System Architecture¶

    Lixy follows a controller-agent architecture pattern, where a central controller manages the desired state and coordinates with distributed agents that execute deployments on LXC hosts.

    Core Components¶

    Controller¶

    The controller is the central management server responsible for:

    1. API Server¶

    • RESTful HTTP API for all operations
    • WebSocket support for real-time updates
    • Authentication and authorization
    • Request validation and error handling

    Location: internal/controller/router.go

    2. GitOps Reconciler¶

    • Monitors Git repositories for changes
    • Parses deployment configurations
    • Compares desired vs. actual state
    • Orchestrates deployment updates
    • Handles drift detection

    Location: internal/services/gitops_reconciler.go

    3. Deployment Service¶

    • Manages deployment lifecycle
    • Stores deployment state
    • Coordinates with agents
    • Tracks deployment history

    Location: internal/services/deployment_service.go

    4. Agent Service¶

    • Manages agent registration
    • Tracks agent health
    • Routes commands to agents
    • Load balancing across agents

    Location: internal/services/agent_service.go

    5. Authentication Service¶

    • User authentication (JWT)
    • Agent authentication (tokens)
    • Role-based access control
    • Session management

    Location: internal/services/auth_service.go

    6. Registry Service¶

    • Manages container registry credentials
    • Issues temporary pull tokens
    • Fetches available image tags
    • Applies version strategies

    Location: internal/services/registry_service.go

    Agent¶

    Agents run on LXC hosts and execute deployment commands:

    1. Agent API¶

    • Receives commands from controller
    • Reports health status
    • Executes deployments
    • Manages local state

    Location: internal/agent/router.go

    2. Container Runtime¶

    • Interfaces with LXC/Docker
    • Pulls container images
    • Manages container lifecycle
    • Handles authentication

    Location: internal/client/container_runtime.go

    Data Storage¶

    SQLite Database¶

    Stores persistent data: - User accounts and credentials - Agent registrations - Deployment configurations - Registry credentials - Authentication tokens

    Location: internal/store/db.go

    Git Repository¶

    Stores infrastructure as code: - Environment configurations - Service definitions - Deployment templates - Version strategies

    Communication Patterns¶

    Controller ↔ Agent¶

    sequenceDiagram
    participant C as Controller
    participant A as Agent

    Note over C,A: Agent Registration
    A->>C: Register (name, metadata)
    C->>A: Registration Token

    Note over C,A: Health Checking
    loop Every 30s
        C->>A: Health Check
        A->>C: Status (OK/Error)
    end

    Note over C,A: Deployment
    C->>A: Deploy Command (compose YAML)
    A->>A: Pull Images
    A->>A: Create Containers
    A->>C: Success/Failure

    Note over C,A: Updates
    C->>A: Update Command (new YAML)
    A->>A: Update Containers
    A->>C: Success/Failure

    GitOps Reconciliation¶

    sequenceDiagram
    participant G as Git Repo
    participant C as Controller
    participant D as Database
    participant A as Agent

    Note over G,A: Reconciliation Cycle

    C->>G: Pull Latest Changes
    G->>C: Updated Files

    C->>C: Parse YAML Configs
    C->>D: Get Current State
    D->>C: Deployment List

    C->>C: Compare States

    alt New Deployment
        C->>D: Create Deployment
        C->>A: Deploy Command
        A->>C: Success
        C->>D: Update State
    else Updated Deployment
        C->>D: Update Deployment
        C->>A: Update Command
        A->>C: Success
        C->>D: Update State
    else Removed Deployment
        C->>A: Delete Command
        A->>C: Success
        C->>D: Delete Deployment
    end

    Security Architecture¶

    Authentication Flow¶

    sequenceDiagram
    participant U as User
    participant API as API Server
    participant Auth as Auth Service
    participant DB as Database

    U->>API: Login (username, password)
    API->>Auth: Validate Credentials
    Auth->>DB: Query User
    DB->>Auth: User Data
    Auth->>Auth: Verify Password (bcrypt)
    Auth->>Auth: Generate JWT
    Auth->>API: JWT Token
    API->>U: Token + User Info

    Note over U,DB: Subsequent Requests

    U->>API: Request + JWT
    API->>Auth: Validate JWT
    Auth->>API: User Context
    API->>API: Check Permissions
    API->>U: Response

    Credential Management¶

    graph LR
    A[Registry Credentials] -->|Encrypted| B[SQLite DB]
    B -->|Decrypt| C[Pull Token Service]
    C -->|Temporary Token| D[Agent]
    D -->|Authenticate| E[Container Registry]
    E -->|Pull Image| D

    Security Features: - ✅ Passwords hashed with bcrypt - ✅ JWT tokens with expiration - ✅ Registry credentials encrypted at rest - ✅ Temporary, scoped pull tokens - ✅ Role-based access control - ✅ Agent authentication tokens

    Deployment Creation¶

    flowchart TD
    A[User Creates Deployment] --> B{Via CLI or API?}
    B -->|CLI| C[CLI Command]
    B -->|API| D[HTTP Request]
    C --> E[Controller API]
    D --> E
    E --> F[Auth Middleware]
    F --> G{Authenticated?}
    G -->|No| H[401 Unauthorized]
    G -->|Yes| I[Deployment Service]

    R --> T[Return Success]
    S --> U[Return Error]

    flowchart TD

    B -->|Auto| D[Git Monitor]
    C --> E[Git Service]
    D --> E
    E --> F[Pull Repository]
    F --> G[Parse YAML Files]
    G --> H[Get Current State]

    I --> J{Changes Detected?}

    J -->|Yes| L[Generate Change Plan]

    O --> Q
    P --> Q
    Q --> R[Update State]
    R --> S[Save to Git State]

    Scalability Considerations¶

    Horizontal Scaling¶

    Agents: Unlimited agents can be registered - Each agent operates independently - Load balanced deployment distribution - Automatic failover to healthy agents

    Deployments: Thousands of deployments supported - Efficient SQLite storage - Indexed queries for fast lookups - Concurrent deployment execution

    Performance Optimizations¶

    1. Git Polling: Configurable intervals to reduce load
    2. Health Checks: Async, non-blocking checks
    3. Database: Indexed columns for common queries
    4. Caching: In-memory caching of frequently accessed data
    5. Concurrent Operations: Goroutines for parallel processing

    High Availability¶

    Controller HA (Future)¶

    • Active-passive failover
    • Shared database backend
    • Session persistence
    • Health check monitoring

    Agent Resilience¶

    • Automatic reconnection
    • Local state persistence
    • Graceful degradation
    • Error recovery

    Monitoring & Observability¶

    Logging¶

    • Structured logging with slog
    • Log levels: DEBUG, INFO, WARN, ERROR
    • Contextual information in all logs
    • Centralized log aggregation ready

    Metrics (Planned)¶

    • Deployment success/failure rates
    • Reconciliation duration
    • Agent health status
    • API request latency

    Health Checks¶

    • Controller health endpoint
    • Agent health monitoring
    • Database connectivity checks
    • Git repository accessibility

    Technology Stack¶

    Backend¶

    • Language: Go 1.21+
    • Web Framework: net/http (standard library)
    • Database: SQLite
    • Authentication: JWT (golang-jwt)
    • Logging: slog (standard library)

    Frontend¶

    • Framework: Vue 3
    • UI Library: Vuetify 3
    • State Management: Pinia
    • HTTP Client: Axios
    • Build Tool: Vite

    Infrastructure¶

    • Containers: LXC/LXD
    • Version Control: Git
    • Container Registry: GHCR, Docker Hub, etc.

    Design Principles¶

    1. Simplicity¶

    • Minimal dependencies
    • Standard library preference
    • Clear, readable code
    • Simple deployment model

    2. Security¶

    • Secure by default
    • Encrypted credentials
    • Token-based authentication
    • Principle of least privilege

    3. Reliability¶

    • Graceful error handling
    • State persistence
    • Automatic recovery
    • Health monitoring

    4. GitOps Native¶

    • Git as source of truth
    • Declarative configuration
    • Automatic reconciliation
    • Drift detection

    5. Developer Experience¶

    • Simple CLI
    • Clear API
    • Good documentation
    • Helpful error messages
